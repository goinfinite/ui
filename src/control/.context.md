Interactive control components — actions and adjustments, not form data collection. Each component configures itself through an all-optional settings struct and drives its visual state from a single Alpine.js `x-data` object.

## Summary

- README.md — Component list and usage snippets for the package
- button.templ — Button with label, static or Alpine-bound aria label, left/right icons, five sizes, a padding override, min/max width and height constraints, three shapes, color and ring styling with a pressed-state background, a `rounded-md` default radius, a shared TextCase label transform, disabled state, click handlers, an always-present type attribute, a hover tooltip rendered through the shared toolset tooltip state, and action states (pending spinner and label, succeeded and failed results) with per-state icon overrides and a pending icon animation class, driven by the promise OnClickFunc returns, by the owning form when IsSubmit is set, or by IsPendingOneWayStatePath
- buttonActionState.js — Alpine data component for the button action states: the click promise tracking, the double-submit guard, native POST and HTMX request tracking for the owning form, the two-second result display, the back-forward cache reset, and the label and icon resolvers that read the passed per-state maps
- rangeSlider.templ — Range slider with min/max/step, single or dual thumbs, and the appearance split into RangeSliderThumbSettings (shape, colors, label, icon, and the value bubble) and RangeSliderTrackSettings (background and fill colors, bounds labels, tick marks, and the hover tooltip)

## Constraints

- MUST render every button with a `type` attribute: `button` by default, `submit` when `IsSubmit` is set
- MUST keep the button action x-data on the `contents` wrapper outside the tooltip wrapper: an x-data on the button would capture the tooltip `x-ref="trigger"`
- MUST react only to HTMX events whose `detail.elt` is the owning form, so a nested hx element in the form does not flip the button state
- MUST render the button tooltip through the shared `uiToolset.TooltipAlpineStateOnce` and `uiToolset.TooltipSurfaceClassesResolver` in the fixed body layer; a scroll container must not clip it or gain a scrollbar from it
- MUST keep the native range inputs in rangeSlider.templ transparent, above the visual thumbs, and as tall as the thumb: they carry keyboard, screen-reader, and drag interaction for the visual thumbs
- MUST split the dual-mode pointer targets with the midpoint clip-path so each native input stays interactive only on its own side of the two thumbs
- MUST resolve rangeSlider.templ thumb aria-labels through `resolveRangeSliderThumbAriaLabel`, which takes one RangeSliderThumbSettings value and falls back from its AriaLabel to its Label to a default name
- MUST build both rangeSlider.templ two-way state watches through `resolveRangeSliderLowerWatch` and `resolveRangeSliderUpperWatch`; each corrects an out-of-bounds state path, and in dual mode pushes the sibling thumb one step past and corrects the sibling state path when the write crosses it
- MUST reuse those same helpers for `ShouldNormalizeInitialState`, which applies the corrections once at init and must stay after the watch registrations so the corrections reach the local thumb values

## Guidance

- SHOULD take the upper thumb appearance from a second `RangeSliderThumbSettings` value, never from a `ThumbUpper*` mirror of a `Thumb*` field
- SHOULD keep each thumb on its own two-way state path: the upper path is ignored without dual mode, and equal paths collapse both thumbs into one
