Interactive control components — actions and adjustments, not form data collection. Each component configures itself through an all-optional settings struct and drives its visual state from a single Alpine.js `x-data` object.

## Summary

- README.md — Component list and usage snippets for the package
- button.templ — Button with a static or Alpine-bound label (LabelOneWayStatePath), static or Alpine-bound aria label, a one-way expanded state path, a FormId form association, top/left/right icons (the top icon and its state path render above the label and combine with the side icons), five sizes whose padding, text, gap, and icon classes come from buttonSizeTokensResolver, IconSizeClass and TextSizeClass overrides for the icon and the label, a padding override, min/max width and height constraints, three shapes, color and ring styling with a pressed-state background, a `rounded-md` default radius, a shared TextCase label transform, disabled state, click handlers, an always-present type attribute, a hover tooltip rendered through the shared toolset tooltip state, action states (pending spinner and label, succeeded and failed results) with per-state label state paths and icon overrides plus a pending icon animation class, driven by the promise OnClickFunc returns, by the owning form when IsSubmit is set, or by IsPendingOneWayStatePath, and a countdown (CountdownSeconds, CountdownTriggerOneWayStatePath) that disables the button, shows the remaining seconds in the label, starts on mount, and restarts when the trigger value changes
- buttonSize.go — buttonSizeTokensResolver mapping each size to its padding, text size, gap, and icon classes plus the padding and icon widths in rem, and the exported ButtonIconOnlyWidthRemResolver that gives callers the icon-only button width for one size
- buttonSize_test.go — Tests for the icon-only width contract and the rendered size classes
- buttonState.js — Alpine data component for the button action states and countdown: the click promise tracking, the double-submit guard, native POST and HTMX request tracking for the owning form or the form named by the button FormId, including a form mounted after init, the two-second result display, the back-forward cache reset, the label resolver that chooses the passed idle, pending, succeeded, or failed expression, the icon resolver that reads the passed per-state map, the remaining seconds, the interval start and stop, the isCounting getter, and the restart on a changed trigger value
- rangeSlider.templ — Range slider with min/max/step, single or dual thumbs, and the appearance split into RangeSliderThumbSettings (shape, colors, label, icon, accessible-name path, and the value bubble) and RangeSliderTrackSettings (background and fill colors, bounds labels, tick marks, and the hover tooltip)

## Constraints

- MUST render every button with a `type` attribute: `button` by default, `submit` when `IsSubmit` is set
- MUST keep the button state x-data on the `contents` wrapper outside the tooltip wrapper: an x-data on the button would capture the tooltip `x-ref="trigger"`
- MUST mount the button state only when the button has an action display or a countdown
- MUST resolve every Button label through `labelExpressionsResolver`, so each label accepts its one-way state path and inherits the idle label when no static label or path is set
- MUST include the four label expressions in the `actionLabelResolver` call in idle, pending, succeeded, failed, external-pending order; the Alpine resolver reads them in that order
- MUST react only to HTMX events whose `detail.elt` is the owning form or the action button, so a nested hx element in the form does not flip the button state
- MUST render the button tooltip through the shared `uiToolset.TooltipAlpineStateOnce` and `uiToolset.TooltipSurfaceClassesResolver` in the fixed body layer; a scroll container must not clip it or gain a scrollbar from it
- MUST keep the native range inputs in rangeSlider.templ transparent, above the visual thumbs, and as tall as the thumb: they carry keyboard, screen-reader, and drag interaction for the visual thumbs
- MUST split the dual-mode pointer targets with the midpoint clip-path so each native input stays interactive only on its own side of the two thumbs
- MUST resolve rangeSlider.templ thumb aria-labels through `RangeSliderSettings.resolveThumbAriaLabel`, which falls back from the thumb AriaLabel to its Label to a default name
- MUST resolve a dynamic thumb aria-label through `RangeSliderSettings.resolveThumbAriaLabelExpression`, which keeps the static AriaLabel resolution as its runtime fallback
- MUST build both rangeSlider.templ two-way state watches through `resolveRangeSliderLowerWatch` and `resolveRangeSliderUpperWatch`; each corrects an out-of-bounds state path, and in dual mode pushes the sibling thumb one step past and corrects the sibling state path when the write crosses it
- MUST reuse those same helpers for `ShouldNormalizeInitialState`, which applies the corrections once at init and must stay after the watch registrations so the corrections reach the local thumb values
- MUST keep each buttonSizeTokens rem width equal to its Tailwind class, so callers reserving space under an icon-only button match the rendered width
- MUST expose the icon-only button width only through ButtonIconOnlyWidthRemResolver: form fields reserve their floating action column through it, so a size-token change reaches them without a second width table

## Guidance

- SHOULD take the upper thumb appearance from a second `RangeSliderThumbSettings` value, never from a `ThumbUpper*` mirror of a `Thumb*` field
- SHOULD keep each thumb on its own two-way state path: the upper path is ignored without dual mode, and equal paths collapse both thumbs into one
